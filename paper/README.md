# DFIP: Decision-Focused Inference Path for System One Models

Four-model review draft.

**Authors:** Ismail Pelaseyed and Alan Zabihi, Superagent Technologies Inc.

The manuscript studies four System One models (also known as decision models): PPLX-Decider v1.1 27B, Liquid d1-3B, Clef-Flash, and GLiNER2.5-Decide. Its question is whether decision-focused inference reduces latency or improves throughput over optimized native execution while preserving the answer fields an application consumes. The paper has not been submitted to arXiv.

The contribution is an empirical systems study applying established techniques
to those four pinned models, with paired native-baseline comparisons, literal
answer audits and separate arrival measurements. Table 1 provides a generated
four-model overview. The results identify workload and fidelity conditions for
usable acceleration, rather than introducing a new CUDA graph algorithm.

`main.tex` and `references.bib` are the editable source; `dfip.pdf` is the compiled review draft. The selected evidence is regenerated by `PYTHONPATH=src python scripts/analyze_focused.py`. Its summary lists the original raw result paths and SHA-256 hashes. Existing experiments outside these four models remain archived in the repository and do not contribute to the manuscript's tables or claims.

The evidence has separate statistical units and workloads:

- The strengthened replay study uses five completed Decider containers, four completed Clef containers with one retained native-preflight failure, and three Liquid compiler-comparison containers. It installs the optional native Qwen kernels and uses the released Liquid compiler setting.
- Direct Decider/Clef answer audits check exposed choices, probabilities, scores and confidence. Resident acceleration does not establish threshold equivalence or performance under changing traffic.
- External varied-traffic tests retain complete request accounting and the failed Decider replay round. A separate post hoc bounded-admission pilot retains the excluded Clef worker-replacement attempt and one validated worker per model.
- GLiNER compares shared scheduling with released native batching. The released compiler follow-up reuses the fixtures after the initial positive result and is exploratory. Its short resident arrival replays are not HTTP or long-duration serving tests.

The phases are not pooled into a single speedup. Native fallback is not reported as acceleration, and retained CUDA failures and numerical drift remain part of the paper. The client defaults remain conservative; this manuscript does not certify production readiness.
