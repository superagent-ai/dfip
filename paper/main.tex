\begin{abstract}
System One models (also known as decision models) return small structured answers, yet their request paths can retain host dispatch, GPU launch overhead, and full-vocabulary projection. Here, we present a decision-focused inference path (DFIP) for PPLX-Decider, Liquid d1-3B, Clef-Flash, and GLiNER2.5-Decide. The implementation combines selective CUDA graph replay, candidate-token projection where the released readout permits it, and schema-compatible length-aware batching. We evaluate full resident requests against stronger native baselines, audit exposed answer fields, and separately measure changing arrivals. With optional native Qwen kernels installed, DFIP achieves short Boolean resident speedups over strengthened native inference of 2.47$\times$ for PPLX-Decider over five containers and 1.45$\times$ for Clef over four of five planned containers; Clef's fifth container fails in native preflight. Liquid is effectively tied with its released compiler setting on the short Boolean workload. Replay supplies most of Liquid's initial eager-baseline gain; projection alone gives little full-request improvement. In separate one-worker GLiNER pilots, length-aware batching is 1.57$\times$ faster than eager native FIFO batching and 1.40$\times$ faster than compiled native FIFO batching on a diverse resident trace, while passing the exposed-label and confidence audit. The compiled arrival replay instead has worse shared-scheduler p95 than native batching. Audits of 3,024 decisions per model preserve all 1,112 returned choices for Decider and Clef, but Clef changes scores, probabilities, and sampled serving confidence thresholds. Diverse external arrivals reverse fixed-shape replay gains and expose overload losses and a replay-path CUDA error. The results identify workload-specific acceleration and its limits, rather than a universal optimizer or production readiness.
\end{abstract}

\section{Introduction}
System One models, also known as decision models, serve routing, policy classification, and structured scoring tasks. An application supplies a state and a small set of questions, and the model returns labels, confidences, or scores. The output is short, but the computation can still include repeated Python dispatch, many small GPU launches, and a projection over tokens unused by the released readout. Reducing this work can lower resident latency and the GPU time required for a workload. The relevant result is an improvement over an efficient native implementation with the application's observable answer contract preserved.

CUDA graphs, compilation, constrained selection, and batching already provide mechanisms for this purpose~\citep{cudagraphs,pygraph,sglang,vllm}. Applying them to System One checkpoints raises practical questions. A graph captured for one shape may be expensive to replace under changing traffic. A smaller projection can preserve a mathematical identity but change floating-point reductions. Batching can reduce total work while increasing a request's wait. A winning label may stay fixed while its confidence crosses an application threshold.

DFIP is a small implementation for studying these effects in four pinned System One checkpoints: PPLX-Decider, Liquid d1-3B, Clef-Flash, and GLiNER2.5-Decide. The models expose different released engines and answer heads. We preserve those interfaces and apply established execution techniques at compatible boundaries. Our objective is acceleration; output checks determine whether a measured improvement is usable under the evaluated contract. Native fallback by itself is not a speed contribution.

We ask three questions. \textbf{RQ1:} Which request paths improve over stronger native baselines, and which components produce the gain? \textbf{RQ2:} Do the accelerated paths preserve exposed answers, including confidence and scores? \textbf{RQ3:} Do resident gains persist under changing arrivals? The contribution is an empirical systems study with an implementation, paired measurements, literal answer audits, arrival accounting, and retained failures. We do not propose a new CUDA graph algorithm or claim transfer to all System One models.

The review repository is \url{https://github.com/superagent-ai/dfip}. Python implements adapters, scheduling, validation, and remote orchestration; Triton~\citep{triton} implements an experimental candidate projection. Checkpoints and corpora stay on Modal. The lightweight local package contains neither weights nor accelerator dependencies. The repository is private at this draft stage; public access and a frozen release remain prerequisites for reproducible submission.

\section{Model Contracts and Scope}
An input contains a state $s$ and typed questions $Q$. For the three generative-backbone checkpoints, a categorical question returns a finite distribution and selected answer, a Boolean question returns confidence in the affirmative answer, and an ordinal question can expose a distribution and expected score. Released prompt format, criterion ordering, token aliases, temperature, and answer conversion are part of the contract.

Liquid's d1-3B uses an LFM-based engine with a packed trunk/branch path for multiple questions. Clef-Flash uses a Qwen backbone and joint schema head. PPLX-Decider uses its released Qwen-based decision engine~\citep{liquid,clef,decider}. GLiNER2.5-Decide uses released schema-conditioned classification~\citep{glinerdecide,gliner2}. Its tested API exposes a winning label and confidence. Six score labels in GLiNER fixtures are categorical buckets; we do not manufacture an ordinal expectation or an unexposed probability vector. Its tested Boolean schema is likewise a two-label classification task.

The study concerns text inputs, unchanged weights, and released/default precision. It does not compare model task quality, train, quantize, or distill a checkpoint. The four-model scope is a focused case study selected after exploratory development, rather than a random sample or unseen-architecture evaluation. Trials for these checkpoints remain in the artifact, including negative results and exclusions. Separate model experiments are outside this paper's claims.

\subsection{Candidate projection and numerical fidelity}
Let $h\in\mathbb{R}^{d}$ be the hidden vector at an answer position and $z=Wh$ the vocabulary logits. For a released readout that groups answer-token aliases $A_c$, consider
\begin{equation}
 r_c=\max_{t\in A_c}z_t,\qquad
 p_c=\frac{\exp(r_c/\tau)}{\sum_j\exp(r_j/\tau)}.
\end{equation}
If $U=\bigcup_c A_c$, computing $W_Uh$ preserves the needed logits in real arithmetic. A vocabulary-wide normalization constant cancels when selected scores are normalized over candidates. This reduction is applicable only when the readout consumes the covered token groups. Arbitrary generation, full-vocabulary confidence, vocabulary-wide top-$k$, or an incomplete alias set require different analysis. A dedicated classification head already avoids this projection.

The identity does not imply finite-precision equivalence. If $\|p-\hat p\|_\infty\leq\epsilon$, an argmax with margin greater than $2\epsilon$ is preserved. A threshold at $a$ is preserved only if $|p_c-a|>\epsilon$. For ordinal levels $v_c$, expected-score drift is at most $\sum_c |v_c|\,|p_c-\hat p_c|$. Separately rounded or computed API fields require direct comparison. We report labels, probabilities, literal confidence, and literal scores when the native API exposes them. Label agreement alone is weaker than preserving a confidence-based application policy.

\section{Execution Paths}
\subsection{Selective replay}
An adapter invokes the released engine at an immutable checkpoint revision. DFIP wraps a compatible tensor boundary with a CUDA graph, static input buffers, and a shape key containing dimensions, strides, dtype, device, and supported scalar metadata. Replays copy the current request into the buffers; the cache stores computation rather than predictions. Calls using mutable buffers are serialized. Clef and Decider use replay around the native backbone without substituting a candidate head. Liquid combines replay with its candidate projection.

The original tested policy admits a shape after three encounters and uses a four-entry least-recently-used cache. All three checkpoints limit capture to 512 tokens; Clef and Decider additionally limit it to one forward row. Decider includes each sequence's non-padding token count in the graph-cache key because its hybrid recurrence launch metadata depends on those lengths. Tensor shape alone cannot establish equivalent control flow. Unsupported paths invoke native inference. These restrictions are part of the measured system, so one admitted short request cannot establish a model-wide speedup.

Allocation lifetime and capture work matter. Earlier Liquid and Clef experiments abort after illegal-memory-access errors. A follow-up synchronizes before clearing or evicting graphs; a synthetic 60-call changed-shape test passes, but this does not prove model-level reliability. The strengthened Decider serving study later encounters a replay-path CUDA error. Asynchronous reporting prevents assigning a kernel cause from those tracebacks alone. Reviewed public inference defaults retain native execution; research entry points expose replay.

\subsection{Candidate readout for Liquid}
The Liquid adapter derives answer-token groups from the released tokenizer and readout. A projection computes the verified union using either a Triton reduction or a PyTorch linear operation backed by cuBLAS. Extending the union invalidates existing captures. To preserve the engine's tensor interface, the prototype reconstructs a vocabulary-shaped tensor with uncomputed positions set to negative infinity. It removes projection arithmetic but retains allocation, scatter, and readout overhead.

Exploratory RMSNorm replacements changed winning labels for Liquid, Clef, and Decider and are not enabled. A local reduction test cannot establish full-model answer preservation: numerical changes can propagate through the backbone and calibrated readout. Released compiler options are tested as baselines rather than presumed slower than custom code.

\subsection{Bounded capture admission}
After varied-serving results, a separate post hoc prototype replaces eviction with a bounded capture budget. It records the last 128 eligible calls and waits for at least 32 observations. A shape requires eight matching hits and frequency at least 12.5\%; each configuration permits at most four capture attempts, including failures. Admitted graphs are pinned. Other shapes execute natively; a new worker or reconfiguration resets the budget.

This policy bounds admission work but does not replace stale shapes when popularity changes. Its tested API accepts one categorical question on one record, with inherited single-row and 512-token limits. It still serializes GPU access and cannot recover a CUDA context damaged by illegal memory access. The one-worker pilot is separate from the original policy.

\subsection{Schema-compatible length-aware batching}
The GLiNER experiment uses its released single and batch calls. An adapter supplies an ordered schema key and input-length estimate. DFIP includes the oldest pending request, prefers compatible requests of similar length, caps batches at eight, caps estimated padded tokens at 8,192, and bounds the longest/shortest length ratio to four. It restores request order and changes neither precision nor the classifier head.

A finite calibration trace admits sizes two, four, and eight separately per ordered schema. Every compared literal field and structure must match. Numerical tolerance is 0.001, with no exposed confidence or probability crossings at 0.1, 0.25, 0.5, 0.75, or 0.9. Each size must exceed 1.10$\times$ serial native speed across three diagnostic timings. Partial batches use only an independently admitted size; new schemas remain singletons. Passing this finite gate does not guarantee arbitrary future inputs and is not a per-request shadow comparison.

The stronger comparator already groups identical ordered schemas into native FIFO batches of up to eight. The incremental question is therefore length-aware selection over native batching. A two-millisecond accumulation window is used in the short arrival replay. These are established scheduling mechanisms integrated with a released decision API, rather than a new general batching algorithm.

\section{Experimental Method}
\subsection{Hardware and native baselines}
Liquid, Clef, and GLiNER run on NVIDIA L40S; PPLX-Decider runs on NVIDIA B200. Each experiment uses one GPU per worker. Strengthened and follow-up jobs use one study GPU at a time. The artifact records GPU identity, driver, CUDA, package versions, container identity, load time, source commit, and mode order. Fresh containers need not use independent physical hosts.

The main replay image uses PyTorch 2.14.0, CUDA 13.0, Triton 3.8.0, and Transformers 5.17.0. For Clef and Decider, it installs \texttt{causal-conv1d} 1.7.0 and \texttt{fla-core} 0.5.2 for released Qwen linear attention~\citep{qwenkernels}. SDPA and Decider's noncausal attention semantics remain intact. Original fallback-image samples are not pooled with this stronger baseline. Changes between images and containers cannot isolate the effect of installing an extension.

Liquid is compared with its released runner's \texttt{torch.compile(mode="reduce-overhead")} setting~\citep{torchcompile}. GLiNER uses \texttt{gliner2} 2.1.0 and released/default FP32 tensors, first eagerly and then with the library's \texttt{compile()} entry point. The compiled GLiNER follow-up is post hoc and reuses the pilot fixtures. These are concrete native comparators, not an exhaustive tuned-serving ceiling.

\subsection{Resident measurements and statistical unit}
For Clef and Decider the strengthened protocol plans five single-use container rounds. Nine workloads cover short Boolean and categorical decisions, three questions on one state, medium and long repeated-log contexts, candidate widths two/eight/sixteen, and eight requests in one batch. Each mode receives 50 timed calls after four admission/warmup calls. Mode and workload orders are randomized within rounds. GPU synchronization brackets resident API timing, including encoding, execution, and native readout; transport and startup are excluded.

The statistical unit is the container round. Each paired speedup is native median latency divided by DFIP median latency; values above one favor DFIP. We pair within-container medians and report the geometric mean of these ratios. The 95\% percentile bootstrap interval resamples paired log ratios 10,000 times; 50 calls are not independent deployment replications. Failed rounds are retained without imputation. Small samples and conditional estimates after attrition limit interpretation.

Liquid's compiler comparison uses three containers and three short workloads. An earlier three-retained-round component ablation compares eager native, replay alone, projection alone, and their combination. The dynamically extended answer union has 40--42 tokens during measurement. This component evidence is not pooled into the compiler comparison. Earlier Liquid and Clef studies each stopped after three rounds following GPU errors; they cannot supply missing repetitions of later protocols.

GLiNER begins with 29 native conformance records, repeated native calls, eight resident cells with 20 warm samples, and single batch probes. The scheduler calibrates on 96 records and evaluates separate 96-record recurring-schema and diverse traces. The latter changes types, option counts, state lengths, and some criterion ordering. Five paired randomized warm timings per trace run in one worker, providing within-worker medians rather than independent-worker intervals. Calibration and evaluation use different state templates, but native architecture and profiling evidence is available before policy design.

\subsection{Answer audits}
For Decider and Clef, 400 cases from pinned \texttt{LocalLLaMA/typed-decisions} supply 2,000 questions. This test set was used during development. Another set derives 512 records and 1,024 decisions from 256 BANKING77 test utterances~\citep{banking}. Widths cycle through two, four, eight, and sixteen and include the gold intent. Each utterance has a single-choice and a choice/Boolean/ordinal view. Boolean targets alternate between matching and nonmatching intents. Ordinal questions are diagnostic without validated score annotations. The correlated views are not independent quality examples, and training overlap is unknown.

A separate instrumented audit compares literal returned choice, score, and confidence plus exposed probabilities on all 3,024 decisions. Clef rounds slots after selecting the categorical answer and computes its score from unrounded probabilities; reconstructing these fields cannot establish literal API equality. The audit uses one container per model with fixed native-then-DFIP order and is separate from timing replication.

Liquid checks 128 changing, unlabeled categorical requests per compiler round, varying content, length, and width; these checks do not cover every Boolean/ordinal timing schema. GLiNER compares labels and confidence with serial native on resident traces and completed arrival requests. Its original pilot archives calibration comparison summaries; individual calibration answers and full serving references are additionally retained in the compiler follow-up. Fidelity results remain finite-sample statements.

\subsection{External arrivals and short resident replay}
The strengthened serving protocol plans three application/container rounds for Decider and Clef. An external workstation with Swedish network egress sends authenticated Modal RPC requests at fixed open-loop rates of five, fifteen, and thirty per second for 60 seconds each. Content, twelve recurring state-repetition counts, and widths two/eight/sixteen change deterministically. This trace can exceed the four-entry cache. Its payloads differ from the resident short Boolean request and do not measure one fixed captured shape.

Workers accept up to 64 concurrent RPC inputs but serialize GPU execution to protect graph buffers. The client allows 128 requests in flight and drops excess arrivals. Each phase drains before the next. Latency starts at scheduled arrival, including dispatch delay, transport, queueing, and response. Initialization and 48 admission calls are separate. Persistent artifacts mean initialization is not an empty-cache download benchmark. Drops and errors remain in the offered denominator; quantiles concern successful requests. Matched successful outputs are audited, with unmatched requests counted separately.

The bounded-admission pilot uses one validated worker each for Decider and Clef in the stronger image. Each mode receives the diverse trace, then a synthetic mix of 60\% recurring short requests and 40\% diversity at the same rates and durations. Content still changes; admission state persists across profiles. Decider runs native first, corrected Clef adaptive first. Clef's first attempt changes worker identity during traffic and finishes on a replacement in native mode. The whole comparison is retained and excluded. An amendment adds worker/mode checks and increases the idle window from ten to 300 seconds before a corrected trial; the replacement cause is unknown.

GLiNER instead receives short resident replays of 256 requests per trace. The recurring trace offers 25/s; the diverse trace alternates 32-request groups at 80 and 20/s. A 128-request queue, two-second deadline, and two-millisecond batch window are fixed. Scheduled-arrival latency includes DFIP length estimation. Reference evaluation warms fixtures beforehand. Arrival windows last approximately eight to eleven seconds without HTTP transport. These results are distinct from the external 60-second phases and do not constitute a long-duration service test.

Decider has zero exposed probability drift, zero changes in 1,112 returned choices, and zero drift in 1,056 scores and 2,168 confidence fields. Clef preserves choices but reaches 0.0188 maximum literal score drift and 0.0129 confidence drift. Probability slots cross 0.1 and 0.25. These are not demonstrated Boolean answer flips, but preclude full probability equivalence.

\section{Changing Arrivals and Serving Limits}
\subsection{Fixed-shape gains reverse under diverse traffic}
Table~\ref{tab:serving} retains observed external phases, including phases from a worker that later fails. Missing phases are not zero-loss successes. Successful-request latency is reported with loss and within-window throughput, so a path cannot appear faster by dropping work.

All three Decider attempts are retained: two complete, and one encounters illegal-memory-access errors in its first graph phase after completing native phases. At five offered requests/s, native loses none and has geometric-mean p95 0.81\,s. Replay gives 2.04 within-window completions/s, 23.0\% loss, and successful-request p95 49.41\,s (range 21.79--76.55\,s). At thirty/s the two observed replay phases lose 83.1\%. All attempts provide 1,761 matched successful pairs with unchanged choices; the two complete graph rounds preserve matched probabilities. This subset cannot certify missing or failed requests.

Recapture explains part of the reversal. One complete attempt records 820 captures and 915 replays including admission and audits, so many replays occur immediately after capture rather than amortizing its cost. At thirty/s its graph service median is 524\,ms versus native 129\,ms. Admission overhead is a bottleneck on this trace; the observations do not locate the fault or establish performance for one recurring shape.

All three Clef serving rounds complete without request errors. At five/s native loses none with p95 0.34\,s; replay loses 4.9\%, completes 2.68/s within the window, and has p95 39.44\,s. At thirty/s replay loses 83.1\% versus serialized native's 54.3\%. This wrapper is not a tuned dynamic-batching ceiling, but the result prevents extrapolating the resident 1.45$\times$ gain to diverse traffic.

\section{Related Work}
SGLang~\citep{sglang} supports structured language-model programs and constrained selection; DFIP does not introduce a decision primitive. PagedAttention/vLLM~\citep{vllm} improves generative serving through memory management and batching. Sarathi-Serve~\citep{sarathi} studies throughput--latency tradeoffs using bounded token work and chunked prefills. Our GLiNER policy uses existing batches and a length budget; it neither implements chunked prefills nor replaces generative scheduling. This motivates native-batch comparisons and queueing measurements rather than serial/batch ratios alone.

PyGraph~\citep{pygraph} studies robust CUDA graph compilation, compatibility transformations, and replay overhead. PyTorch documents static-address and control-flow restrictions~\citep{cudagraphs}. Our shape cache and empirical admission are simpler integrations with exposed limitations. Triton~\citep{triton} provides tiled programming; Liquid's ablation shows that reducing projection scope need not appreciably accelerate a full request.

GLiNER2~\citep{gliner2} supplies a schema-driven encoder architecture with classification and task composition. It contextualizes the newer pinned Decide checkpoint; published CPU results are not its implementation identity or our GPU baseline. MLPerf Inference~\citep{mlperf} emphasizes scenarios, quality constraints, and distinct latency/throughput metrics. We follow that separation without claiming compliance. BANKING77~\citep{banking} supplies an independently sourced intent corpus; our typed schemas and ordinal diagnostics are derived workloads.

\section{Limitations and Deployment Implications}
\textbf{Baselines and selection.} Native Qwen kernels and released compilers address specific weaknesses of eager-only comparisons but do not exhaust optimized backends. Four checkpoints selected after development cannot establish unseen-architecture transfer. Prompt and workload differences prevent pooling a cross-model speedup. Clef's missing native round and earlier errors make retained estimates conditional.

\textbf{Serving scope.} Synthetic states emphasize particular paths. External tests use one geography, fixed rates, serialized GPU wrappers, and minute-scale phases. They do not establish a tuned dynamic-batching ceiling, hours-long reliability, or autoscaling. Bounded-admission pilots have one validated worker per model, history-dependent traces, and fixed differing mode orders; no direct eviction-versus-pinned trial isolates the policy effect. GLiNER has one worker per substrate, warmed second-scale replays, and reused fixtures in the post hoc compiler follow-up.

\textbf{Numerical scope.} Rounding, calibration, and reductions can separate label agreement from literal field equality. Five thresholds do not cover arbitrary policies; calibration and subsequent agreement are finite observations. Dataset views correlate, the typed set was used in development, and training overlap is unknown. Native agreement evaluates implementation fidelity. Establishing preservation of task accuracy, calibration quality, and downstream utility beyond the tested samples requires representative, task-specific labeled evaluation.

\textbf{Reliability and cost.} CUDA errors may be reported after the faulting operation. Archived traces cannot assign a kernel cause; synthetic lifetime checks cannot certify full engines. Native fallback cannot repair a poisoned context. GPU-time savings can reduce one compute-cost component, but no billed savings are measured: load, admission, host resources, idle lifetime, queueing, and retries also matter. The evidence supports opt-in workload-specific experiments with native execution as the reviewed default and application confidence policies checked explicitly.

\textbf{Reproducibility.} Revisions, source snapshots, manifests, samples, and failed attempts are archived. Cloud placement, clocks, contention, transitive dependencies, and drivers remain partly uncontrolled. Authors must verify generated claims, freeze an accessible artifact, and review failures and drift before submission. The manuscript remains a review draft.

\section{Conclusion}
DFIP demonstrates workload-specific acceleration for four released System One interfaces using established execution techniques. Selective replay improves repeated short Decider and Clef requests over stronger native kernels, but not the tested diverse serving traffic. Liquid's released compiler closes most of its eager gap; candidate projection alone contributes little. Schema-compatible length-aware batching retains a 1.40$\times$ diverse resident gain over compiled native FIFO batching for GLiNER, while worsening the tested compiled arrival tail. Probability and confidence changes, attrition, and GPU errors define concrete limits. The results favor selecting an execution path per native contract and workload, comparing with efficient native execution, and validating the fields consumed by users. General acceleration and production readiness require independent serving and numerical validation.
